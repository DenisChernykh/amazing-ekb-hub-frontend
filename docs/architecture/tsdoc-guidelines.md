# TSDoc гайд (Balanced)

Этот документ фиксирует формат отдельной TSDoc-задачи: она запускается только
по явному запросу и не является требованием обычной разработки или стандартного
lint.

## Цель

- Быстро понимать поведение экспортируемых функций, компонентов, хуков и типов без чтения всей реализации.
- Явно документировать `null` / `undefined` ветки, fallback-состояния и side effects.
- Не превращать комментарии в шум.

Перед началом такой задачи запустите:

```bash
pnpm run lint:tsdoc
```

Команда выводит замечания как warnings и не входит в `pnpm run lint` или
`pnpm run lint:strict`.

## Область применения

- В рамках явно запрошенной TSDoc-задачи пишем TSDoc для экспортируемых сущностей:
  - `export function`
  - `export const`, если это публичный API модуля
  - `export type`
  - `export interface`
  - `export enum`
- Для экспортируемых React-компонентов:
  - function components
  - arrow-function components
  - `forwardRef` components
  - экспортируемые `*Props` типы и интерфейсы
- Для приватных helper-ов:
  - комментарий нужен только если логика неочевидна
  - иначе без комментария

## Язык и стиль

- Язык описаний: русский.
- Идентификаторы, названия типов и inline-код пишем как в коде, обычно на английском, в обратных кавычках.
- Summary должен быть коротким: 1–2 строки про назначение и контракт.
- Не пересказываем реализацию построчно.
- Пишем про контракт и поведение, а не про очевидные детали.

## Обязательный минимум по тегам

Для каждого экспортируемого API:

- краткий summary обязателен.

Для экспортируемых функций и хуков:

- `@param` добавляем для нетривиальных параметров;
- `@returns` добавляем, если у результата есть смысловой контракт, особенно для `null`, `undefined`, fallback или специальных веток;
- `@remarks` добавляем, если есть side effects, ограничения или важный контекст;
- `@typeParam` обязателен для значимых generic-параметров;
- `@example` добавляем только когда пример реально помогает понять формат входа или выхода.

Для экспортируемых типов и интерфейсов:

- summary обязателен;
- `@typeParam` обязателен для generic-типов.

## Компоненты (React / TSX)

### Что документируем

- экспортируемые компоненты;
- экспортируемые `*Props` типы и интерфейсы;
- экспортируемые UI-хуки;
- `forwardRef` компоненты, если они составляют публичный UI API.

### Как писать TSDoc для компонентов

- `summary` обязателен для каждого экспортируемого компонента и `*Props`.
- `@param` нужен только для нетривиальных пропсов:
  - режимы поведения;
  - callback-контракты;
  - controlled / uncontrolled поведение;
  - пропсы, влияющие на ветки рендера;
  - fallback-тексты или состояния.
- Тривиальные pass-through пропсы вроде `className`, `children` и стандартных HTML-атрибутов не нужно документировать поштучно без явной необходимости.
- `@returns` нужен только если есть важная контрактная ветка рендера:
  - `null`;
  - early return;
  - `loading`, `empty`, `error` как часть публичного поведения.
- `@remarks` нужен, если:
  - есть side effects;
  - есть `ref`-контракт;
  - компонент требует provider или иного контекста;
  - есть ограничения использования.
- `@typeParam` обязателен для generic-компонентов.

## Какие теги не использовать по умолчанию

Не добавляем без реальной необходимости:

- `@public`
- `@private`
- `@deprecated`
- `@throws`, если исключения не являются явной частью контракта

## Parser pitfalls

Для `@example` не используем сырые object literal строки без fenced code block.

Плохо:

```ts
@example
const x = { a: 1 };
```

Хорошо:

````md
@example

```ts
const x = { a: 1 };
```
````

Иначе `tsdoc/syntax` может интерпретировать фигурные скобки как inline tag.

## Шаблоны

### Экспортируемая функция

```ts
/**
 * Выполняет действие и возвращает нормализованный результат.
 *
 * @param input - Входные данные и ожидания к ним.
 * @returns Нормализованный результат или `undefined`, если данные отсутствуют.
 */
```

### Экспортируемый generic type

```ts
/**
 * Нормализованное представление результата фильтрации.
 *
 * @typeParam TValue - Тип полезного значения.
 */
export type FilterResult<TValue> = {
  value: TValue;
};
```

### Экспортируемый компонент

```tsx
/**
 * Рендерит панель фильтров для списка мест.
 *
 * @param onReset - Вызывается при сбросе фильтров.
 * @returns `null`, если фильтры недоступны в текущем состоянии.
 */
export function PlacesFilters({ onReset }: PlacesFiltersProps) {
  // ...
}
```

### `forwardRef` компонент

```tsx
/**
 * Рендерит текстовый input с пробросом `ref` к нативному элементу.
 *
 * @remarks `ref` указывает на `HTMLInputElement` и используется внешними формами для фокуса.
 */
export const TextInput = forwardRef<HTMLInputElement, TextInputProps>((props, ref) => {
  // ...
});
```

## Антипаттерны

- Пустой комментарий без полезной информации.
- Комментарий, который просто повторяет имя функции или типа.
- Комментарий, который не соответствует реальному поведению кода.
- Избыточное документирование тривиальных пропсов и очевидных деталей реализации.
- Самодельные теги без явной договорённости в проекте.

## Чеклист TSDoc-задачи

1. У каждого выбранного для задачи экспортируемого API есть summary.
2. У функций и хуков описаны нетривиальные параметры и важные ветки результата.
3. У generic API есть `@typeParam`.
4. `@remarks` добавлен там, где есть side effects или ограничения.
5. `@example` используется только там, где без него контракт сложнее понять.
6. Комментарий объясняет контракт, а не пересказывает реализацию.
7. `pnpm run lint:strict`
8. `pnpm run typecheck`
9. `pnpm run build`
